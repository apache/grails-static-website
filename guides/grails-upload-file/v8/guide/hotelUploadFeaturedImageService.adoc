The service uploads the file with the `S3Client`, then stores the key and URL:

[source, groovy]
.grails-app/services/example/grails/UploadHotelFeaturedImageService.groovy
----
include::../snippets/grails-app/services/example/grails/UploadHotelFeaturedImageService.groovy[indent=0]
----

<1> The `S3Client` bean from `resources.groovy` is injected by name.
<2> The bucket name is read from the configuration.
<3> The hotel is loaded first. If it does not exist, nothing is uploaded.
<4> If the hotel has a higher version than the form sent, the upload is rejected before anything is sent to S3. `updateFeaturedImage` checks the version again in its transaction, for an update that happens while the file is being uploaded.
<5> A random UUID in the key gives every upload its own object and URL. Uploading a file with the same name again does not overwrite the current image, and browsers and CDNs do not keep showing a cached copy of the old one.
<6> `putObject` streams the uploaded file to S3, with its content type. The SDK does not close the stream, so `withCloseable` closes it. Otherwise the temporary file Tomcat keeps for a large upload stays open until the garbage collector runs.
<7> The SDK builds the object's URL for the configured region or endpoint.
<8> A GORM Data Service stores the key and URL.
<9> If the hotel cannot be updated, or the update throws an exception, the new object is deleted from S3 again. The current image is not touched.
<10> After a successful update, the previous object is deleted. As for the point of interest, this relies on the service not being transactional.
