[source, groovy]
.grails-app/services/example/grails/UploadPointOfInterestFeaturedImageService.groovy
----
include::../snippets/grails-app/services/example/grails/UploadPointOfInterestFeaturedImageService.groovy[indent=0]
----

<1> `GrailsConfigurationAware` gives the service the configuration when the application starts.
<2> The point of interest is loaded first. If it does not exist, no file is written.
<3> If the point of interest has a higher version than the form sent, the upload is rejected before the file is written. `updateFeaturedImage` checks the version again in its transaction, for an update that happens while the file is being written.
<4> A random UUID in front of the sanitized file name gives every upload its own file and URL. Uploading a file with the same name again does not overwrite the current image, and browsers do not keep showing a cached copy of the old one.
<5> `transferTo` writes the uploaded file to its path in the folder. The path uses the sanitized file name, so it cannot point outside the folder.
<6> A GORM Data Service updates `featuredImageUrl`.
<7> If the point of interest cannot be updated, or the update throws an exception, the new file is deleted again. The current image is not touched.
<8> After a successful update, the previous image is deleted. This is safe because the service is not transactional, so the update is already committed when `updateFeaturedImage` returns. If you add `@Transactional` to the service, the update commits only when `uploadFeaturedImage` returns, and a rollback would leave the point of interest pointing at a deleted file. In that case, delete the previous file after the commit, for example from the `afterCommit` method of a `TransactionSynchronization`.
<9> `deleteFileByUrl` finds the file from its URL, and only deletes files inside the folder.
