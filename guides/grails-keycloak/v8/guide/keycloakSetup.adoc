This chapter covers the Keycloak configuration used by the example application: running Keycloak with `start-dev`, the realm and client, roles, the client role mapper, and test users.

Keycloak `start-dev` keeps its own embedded database. No external database setup is required.

See the example repository's `KEYCLOAK.md` for a longer Keycloak setup (systemd and SMTP).

== Assumptions

The examples below assume:

[cols="1,2"]
|===
| Component | Value
| Keycloak URL | `http://localhost:8081`
| Grails application | `http://localhost:8080`
|===

If your installation uses different ports or hostnames, replace them throughout.

NOTE: This guide assumes a Linux installation. Keycloak runs the same on Windows, but the commands differ: use `bin\kc.bat start-dev` instead of `bin/kc.sh start-dev`, run it from a console (see https://www.keycloak.org/getting-started/getting-started-zip[Getting Started with Keycloak] and https://www.keycloak.org/server/installation[Server Installation and Configuration]). Alternatively, install https://learn.microsoft.com/windows/wsl/install[WSL] and run the Linux commands in this guide as-is.

== Prerequisites

Before configuring Keycloak, you should have:

* Java installed
* Keycloak installed (Keycloak 26+)
* The Grails example application

== Start Keycloak

From the Keycloak installation directory, start Keycloak in development mode:

[source,bash]
----
bin/kc.sh start-dev --http-port=8081
----

On Windows:

[source,bash]
----
bin\kc.bat start-dev --http-port=8081
----

`start-dev` uses an embedded H2 database. No database configuration is needed.

== Access the Keycloak administration console

Once Keycloak is running, open `http://localhost:8081` and log into the administration console using the Keycloak administrator account.

If you are accessing Keycloak from another machine, replace `localhost` with the hostname or address where Keycloak is running.

== Create the example realm

From the Keycloak Administration Console, create a new realm:

```text
Realm name:
example
```

The OpenID Connect issuer for the realm is:

```text
http://localhost:8081/realms/example
```

This value becomes the Grails application's `KEYCLOAK_ISSUER` environment variable.

== Create the OpenID Connect client

Navigate to **Clients → Create client** and create an OpenID Connect client:

```text
Client type:
OpenID Connect

Client ID:
example-client
```

The `Client ID` becomes the Grails application's `KEYCLOAK_CLIENT_ID` environment variable.

=== Enable client authentication

Enable client authentication for the client. Keycloak generates a client secret. That secret becomes the Grails application's `KEYCLOAK_CLIENT_SECRET` environment variable.

Do not commit the client secret to Git.

=== Configure redirect URIs

For the example application running locally on port `8080`, configure the redirect URI:

```text
http://localhost:8080/login/oauth2/code/keycloak
```

This is the OAuth2 login callback used by the Grails application. If you run the application on a different URL, change the redirect URI accordingly.

=== Configure web origins

For local development, configure:

```text
http://localhost:8080
```

as the web origin. Do not use unrestricted origins unless they are specifically required.

== Create the client roles

This example uses client roles rather than realm roles.

=== USER role

Navigate to **Clients → example-client → Roles** and create:

```text
USER
```

Do not create this under **Realm roles**. The application uses `USER` for normal authenticated users:

[source,groovy]
----
@PreAuthorize("hasRole('ROLE_USER')")
----

=== ADMIN role

Under **Clients → example-client → Roles**, create:

```text
ADMIN
```

The client now contains `USER` and `ADMIN`. The application protects administrator-only functionality with:

[source,groovy]
----
@PreAuthorize("hasRole('ROLE_ADMIN')")
----

=== Make ADMIN inherit USER

Keycloak supports composite roles. Configure `ADMIN` as a composite role containing `USER`.

Navigate to **Clients → example-client → Roles → ADMIN** and add `USER` as an associated/composite role.

The resulting structure is:

```text
example-client
│
├── USER
│
└── ADMIN
    └── USER
```

A user assigned `USER` has the effective roles:

```text
USER
```

A user assigned `ADMIN` has the effective roles:

```text
ADMIN
USER
```

The administrator does not need `USER` assigned separately. This lets the application secure ordinary functionality with `ROLE_USER` while administrator-only functionality requires `ROLE_ADMIN`.

== Create test users

=== test-user

Navigate to **Users → Add user** and create:

```text
Username:
test-user

Email:
test-user@example.com
```

Set a password under **Credentials**.

Open the user, navigate to **Role mapping**, select the `example-client` client roles, and assign:

```text
USER
```

The user should have:

```text
Direct role:
USER

Effective roles:
USER
```

=== test-admin

Create another user:

```text
Username:
test-admin

Email:
test-admin@example.com
```

Assign only `ADMIN`. Do not separately assign `USER`. Because `ADMIN` contains `USER`, the effective roles should be:

```text
Direct role:
ADMIN

Effective roles:
ADMIN
USER
```

== Add the client role mapper

Creating the roles is not enough. The client roles must also be included in the OpenID Connect tokens consumed by the Grails application.

Navigate to **Clients → example-client → Client scopes → Dedicated scopes** and add a mapper for the client roles, configured for the `example-client` client.

=== Configure the mapper

Configure the mapper with the following settings:

|===
| Setting | Value

| Add to ID token
| On

| Add to access token
| On

| Add to lightweight access token
| Off

| Add to userinfo
| On

| Add to token introspection
| On
|===

The final configuration is:

```text
Add to ID token:                  On
Add to access token:              On
Add to lightweight access token:  Off
Add to userinfo:                  On
Add to token introspection:       On
```

=== Verify the token with Evaluate

Before troubleshooting the Grails application, verify that Keycloak puts the roles into the token.

Navigate to **Clients → example-client → Client scopes → Evaluate** and select `test-user`.

The Evaluate screen shows the token Keycloak would issue for that user. The `test-user` should show the `USER` client role:

```text
USER
```

Select `test-admin` and evaluate again. Because `ADMIN` contains `USER`, the `test-admin` should show both roles:

```text
ADMIN
USER
```

The client roles are typically represented in the token under `resource_access`. For example:

[source,json]
----
{
  "resource_access": {
    "example-client": {
      "roles": [
        "USER"
      ]
    }
  }
}
----

An administrator has something similar with both roles:

[source,json]
----
{
  "resource_access": {
    "example-client": {
      "roles": [
        "ADMIN",
        "USER"
      ]
    }
  }
}
----

The exact token output varies by Keycloak version and configuration.

TIP: After changing roles or mapper settings, log out and log back in so that a new token is issued.

== Troubleshooting

=== Keycloak does not start

Check the Keycloak logs for errors. Common causes include:

* Port 8081 is already in use
* Java is not installed or not on the PATH
* The Keycloak installation is incomplete

=== Roles are missing from the application

Start with Keycloak rather than Grails. Use **Clients → example-client → Client scopes → Evaluate** to inspect the token for the affected user.

If the roles are missing from Evaluate, the problem is in Keycloak. Check:

* The roles are client roles.
* The roles belong to `example-client`.
* The user has the expected role.
* `ADMIN` contains `USER`.
* The client role mapper exists and is configured for `example-client`.
* Add to ID token, access token, userinfo, and token introspection are On; lightweight access token is Off.

If the roles appear correctly in Evaluate but the Grails application does not recognize them, the problem is likely in the application authority mapping (see the snippets chapter).

=== ADMIN does not have USER permissions

Verify that `ADMIN` → `USER` is a composite role:

```text
ADMIN
└── USER
```

Then use **Clients → example-client → Client scopes → Evaluate** to verify that an administrator has both `ADMIN` and `USER` effective roles.

=== Redirect URI errors

Verify that the Keycloak client contains the exact redirect URI the Grails application uses:

```text
http://localhost:8080/login/oauth2/code/keycloak
```

The URI must match the application's actual URL.

== Configuration summary

The complete Keycloak configuration for the example is:

```text
Keycloak (start-dev, embedded H2)
│
└── example realm
    │
    └── example-client
        │
        ├── USER
        │
        └── ADMIN
            └── USER
        │
        └── Client Role Mapper
            ├── ID Token: On
            ├── Access Token: On
            ├── Lightweight Access Token: Off
            ├── Userinfo: On
            └── Token Introspection: On
```

The most important pieces are:

1. Keycloak `start-dev` keeps its own embedded database, so no external database setup is needed.
2. `example` is the Keycloak realm, and `example-client` represents the Grails application.
3. `USER` and `ADMIN` are client roles, and `ADMIN` is a composite role containing `USER`.
4. A client role mapper places the roles into the OIDC tokens.
5. The Evaluate screen verifies the token before you troubleshoot Grails.
6. Spring Security maps the Keycloak roles to authorities such as `ROLE_USER` and `ROLE_ADMIN`.
7. `@PreAuthorize` controls access within the Grails application.

When the realm, client, roles, and mapper are configured, continue with the Grails application configuration described in the next chapters.
